## 本次实现

### 内存与完整诊断

1. 修复重启时的日志读取峰值：读取上轮 native 日志尾部时，直接定位到最后 8 KiB，不再先加载整份日志。
2. 代码缓存新增 **512 MB**，保留 **1 GB / 1.5 GB**。这是实际传给 JIT 分配器的大小。对于物理内存不超过 8 GiB 的 iPad，没有历史选择时默认 1 GB；用户已有的显式选择继续保留。更小缓存可能增加翻译缓存刷新、降低运行速度。
3. 每 30 秒记录一次进程物理占用、驻留内存、可分配余量和温度状态，记录内存警告及前后台事件。采样使用独立队列。
4. “Export diagnostics” 导出一个文本附件，包含当前和上轮 App 启动的 `henge.log`、native 日志和版本/配置/采样元数据。每份来源按导出开始时的文件长度流式读取，不只截取末尾几十行。
5. Details 内新增 “Mark missing input candidates”，记录候选框不可见的复现时刻，以及输入/显示状态，不录入输入内容或截图。

“Allocation headroom” 是进程还能分配多少内存的估计，不等于物理空闲 RAM，也不能单独证明 Jetsam。App 无法捕获 SIGKILL；闪退原因仍需对照 iPadOS 的 `.ips` / Jetsam 报告。

### 宿主服务第一阶段

复用现有 Henge 共享服务的 guest-only 通道：macOS 访问 `10.0.2.4`，经虚拟网络转入 App 的私有 Unix socket。

| 接口 | 本次行为 |
| --- | --- |
| `GET /.henge/v1/capabilities` | 返回真实实现的能力与当前会话标识 |
| `GET /.henge/v1/state` | 读取 iPad 主屏亮度、输出音量及会话状态 |
| `POST /.henge/v1/brightness` | 经本次会话的显式开关授权后，调整 iPad 主屏亮度 |

亮度通过 UIKit 的 `UIScreen.brightness` 调整。写入要求当前 VM 正在运行、App 处于活动状态、用户已打开开关、会话标识匹配。请求有大小与时间上限；超时或已撤销的排队请求不会在稍后重新应用。会话标识用于拒绝旧会话请求，不隔离同一虚拟机内的不同进程。

输出音量本次只读。能力响应明确标记 Wi-Fi、蓝牙、Apple 账号和 DeviceCheck 为未实现。没有打包或运行来路不明的 deb 可执行文件，也没有改动 Chat 的签名或设备认证判断。

## 安装前与首次运行

1. 保留当前可用的 0.3.0 安装包。对需要保留的 Mac 使用 Henge 的导出功能备份；**不要先删除已有 Henge App**。
2. 核对下载包的 SHA-256、manifest 中的 `0.4.0 / 4001`、源码提交和构建时间。安装包尚未生成时，源码 ZIP 或 Git bundle 不能用作 TIPA 安装。
3. 用 TrollStore 安装实际构建产物 `Henge.tipa`。继续使用你原来已可工作的 JIT 启动方式。
4. 首次测试先保持现有 VM、内存和显示设置。只改变一个参数，便于和 0.3.0 比较。
5. 代码缓存设置要在完全退出并重新打开 Henge 后才生效；只重启 guest macOS 不够。

## 测试步骤

### A. 候选框与闪退

1. 启动现有 macOS，在“文本编辑”等 App 中输入 `nihao`，先不按空格。
2. 若仍看不到候选框，到 Henge > Details 点击 “Mark missing input candidates”，记住大约时间，再回到 macOS 按空格确认是否仍输出“你好”。
3. 保持与以前相同的工作负载，先测试 1 GB 缓存。若要对照 512 MB，完全退出 Henge 后修改/重开，并记录是否变慢、是否仍闪退。
4. 若 Henge 退出，**只重新打开一次，先不要启动 Mac，立即到 Settings > Diagnostics 导出**。等待报告生成，再点 “Share diagnostics” 保存或分享。再次重启 App 会轮换上一轮日志。
5. 附上相近时间的 iPadOS 分析报告。可在“设置 > 隐私与安全性 > 分析与改进 > 分析数据”寻找 Henge 或 JetsamEvent 对应文件。仅截取日志最后一行不足以区分内存回收、异常、GPU 问题和 watchdog。

导出时会过滤常见凭据、输入载荷、URL、邮箱和私人路径，但不承诺完全匿名。分享前可先检查文本；不需要发送 Apple 账号密码、令牌或 pairing record。

### B. 宿主亮度桥接

在运行中的 Mac 打开终端，通过 Henge Details > Sharing 的原有设置命令更新 guest helper。重新执行设置会替换 helper，保留共享目录。

读取能力和状态：

```sh
"$HOME/Library/Application Support/Henge/henge-agent" --host-capabilities
"$HOME/Library/Application Support/Henge/henge-agent" --host-state
```

在 Henge > Details > iPad services 打开 “Allow Mac to change iPad brightness”，再在 guest 终端执行：

```sh
"$HOME/Library/Application Support/Henge/henge-agent" --host-brightness 0.6
```

预期为 iPad 主屏亮度变到约 60%，命令返回宿主实际亮度。关闭授权或结束 VM 会话后应拒绝写入；取消授权或会话结束时，只在亮度仍等于桥接最后设置值时恢复之前的亮度，以保留用户随后在控制中心做的调整。

### C. Chat 设备认证

可以原样复测 Chat，但本版没有实现 DCDevice/DeviceCheckInternal 的真实宿主认证代理，因此**不把 `devicecheck_unsupported_device` 消失作为已实现功能**。读取或替换普通 iPad 型号、序列号、Wi-Fi、蓝牙参数不会自动生成有效认证令牌。VirtualMac deb 的账号代理链路是否适用于当前 Chat 原生模块，仍需单独验证。

## 构建

需要可用的 macOS / Xcode 27 构建环境。此仓库的 Actions 工作流保留了该下游成功构建使用的 `xcode-27` runner 标签；其他账户或 fork 是否有该 runner，必须实际确认。

Husk 依赖固定为 `29abb512d81bf8cc08babcbe7f7007cb557208ef`，该 SHA 来自上述成功构建的实际 checkout 日志。该次构建使用 Xcode 27.1 和 iPhoneOS 27.1 SDK，App 的最低运行版本仍为 iOS 17.0。

推送专用分支 `work/0.4-ipados17-test` 会触发构建；也可以在包含该工作流的仓库中选择 Actions > **Build Henge 0.4 test packages** > Run workflow，再选择测试分支。默认构建 TIPA，手动启动时可额外选择 IPA。流程会运行新增自动测试、编译依赖和 App、进行签名/包检查，并上传包、SHA-256、manifest 和构建日志。失败时也会保留日志。

本地已有已编译 Husk 依赖时，原有构建入口仍然适用：

```sh
export HUSK="/absolute/path/to/Husk"
zsh ios/scripts/fetch_deps.sh
zsh tools/build_ios_restore.sh
make ios-lib
zsh ios/scripts/package_ipa.sh --trollstore
```

打包前必须提交源码，使包内的 Git 提交信息对应实际代码。默认输出 `~/Desktop/Henge.tipa`；可用 `HENGE_PACKAGE_OUTPUT_DIR` 改到单独目录。不要用旧版本二进制改 Info.plist 冒充 0.4，也不要在编译失败后分发残留产物。
